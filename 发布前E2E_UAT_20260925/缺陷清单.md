## F-03 【P1】重复发码复用已消费的 Turnstile token → 403「人机验证失败，请重试」死循环

- **现象（字节级）**：第二次点「发送验证码」，请求携带与第一次**完全相同**的 token（前缀 `1.UBJd_35L4q7V4BT0L…`，两次逐字一致），响应 HTTP 403 `{"message":"人机验证失败，请重试","success":false}`。
- **源码根因**：`takeCaptchaToken()` 取走 token 后调 `reexecTurnstile()` 重挂组件，但实测重挂后 widget 回调写回的是**同一个缓存 token**（Turnstile re-execute 在未过期窗口内可回发相同 token）；后端 `siteverify` 对已消费 token 判失败。前端无 reset 兜底，用户侧表现为「点一次说人机验证失败」且反复如此。
- **误导面**：真实原因是 token 复用，但文案把用户指向"再验证一次"，而页面上根本没有可再操作的验证框。
- **修法前置**：失败分支应调 `turnstile.reset()` 强制领新 token（或禁用重发按钮 60s 对齐后端冷却）。

## F-30 【P1】登录暴力破解锁定在生产链路不达标：前 5 次失败后第 6 次仍正常走密码校验（未拦），到第 10 次请求才见「登录尝试过于频繁」

- **现象（线上实测，B8 收口）**：同浏览器连续 9 次错密码（约 5 分钟内，均「用户名或密码错误」），第 10 次提交**正确密码**才被 `429 登录尝试过于频繁，请稍后再试` 拦截；冷却后正确密码可恢复登录（自愈成立）。
- **与文档口径的差**：代码 `ratelimit.go` `loginFailThreshold=5`——第 5 次失败落库即应设锁、第 6 次请求必拦；实测第 6 次未拦。最可能解释是**限流键不稳定**：`clientIP` 取 XFF 第一跳（生产 `TRUST_PROXY_XFF=1`，见《生产配置清单》），而测试出口是 IPv6 隐私地址（Cloudflare 错误页实测 `2408:820c:…`），接口标识按连接轮换时失败计数被打散到多个键，攒够同一键的 5 次才落锁。
- **为什么不能直接修**：需线上取证（`rate_limits` 表 login_fail 行的 key 分布 + 单位 env + 访问日志 XFF 首跳样本）才能定性是「键漂移」还是「二进制落后于源码」；本批审计纪律不动线上配置。
- **修法前置**：① 服务器侧取证三件套（见上）；② 若键漂移坐实，登录失败防护加**用户名维度**计数（IP∪username 双键），并考虑登录页失败 ≥2 次后挂 Turnstile（当前登录页无任何人机验证，锁定是唯一防线）；③ 补一条 UAT 断言：同键 5 败后第 6 次必 429。

> **F-30 取证结论（2026-09-26 01:2x，服务器只读实测，键漂移坐实）**：
> ① **运行态开关**：`TRUST_PROXY_XFF=1` 已在 translator 进程环境中（不是「没开信任」的问题）。
> ② **键分布**：`rate_limits` 全表逐条归类（login_fail/guard_int/guard_day 的 email-code·lead·pwd-forgot 前缀），键 IP **全部落在 Cloudflare 回源段**（104.22.x、108.162.x、162.158.x、172.67–172.71.x），无任何真实客户 IP——即后端 `clientIP()` 拿到的 XFF 首跳本身就是 CF 回源 IP，**全体客户被合并进 CF 池若干共享桶**。
> ③ **伪造探针**：`X-Forwarded-For: 203.0.113.77` 送 `/api/lead`（400 触发计数）后表中**无该键**——上游把客户端自带 XFF 清洗/覆盖了 ⇒ 好消息：不存在「伪造头绕过限流」；坏消息：真客户 IP 根本到不了首跳。
> ④ **定性**：登录 5/300s 阈值按 CF 回源 IP 计数——同一回源 IP 上多个客户互相污染（一人失败五人吃 429 的串扰面 + 桶随 CF 池轮换根本锁不住单一攻击者），B8 实测「第 6 次不拦、第 10 次才见频控」正是失败被摊薄到多个 CF 桶所致。**F-30 维持 P1**。
> ⑤ **修法（待令，未施工）**：Caddy 各 `reverse_proxy` 块对 CF 来源显式改写 `header_up X-Forwarded-For {http.request.header.CF-Connecting-IP}`（CF 对该头写真实客户 IP 且不可伪造），**前置条件**＝源站 443 防火墙只放 CF 段（否则直连源站者可伪造该头）；或后端加 CF 部署形态判据优先读 `CF-Connecting-IP`。改动属部署级（Caddy/env），不在本轮授权范围，挂账待用户拍板。

- **现象（生产实测一型，字节级留证）**：余额 2,000 积分时经 `POST /openapi/v1/tasks`（JSON，Bearer rk_0e2e…，mode=pro，3 语种，43,572 字符）提交任务 90。烧穿上限后工单终态 = **status=`completed` + reject_reason=`context canceled` + tokens_billed=0**；`/openapi/v1/tasks/status?id=90` 对外回**成功形态** `{"status":"completed","points_used":0,"translations":{"en":"","ja":"","ko":""}}`——外部集成方按契约分支会把「零交付的空译文」当成功消费。对照面：同型载荷在 UI 工单路径结局是 rejected+`insufficient_balance:` 前缀（工单 88/89），**API 任务路径独有假 completed**，且文档承诺「failed→insufficient_balance 出参」在此永不触发。
- **根因（源码四层逐环读死，非推测）**：① 余额钩子中止后，管线步骤间隙 `orchestrator/flow.go:122-123 return ctx.Err()` 把**裸 `context canceled`** 作为 runErr 上抛（与 88 型「worker 收尾前预检拒绝」不同路径）；② `service/ticket.go:363-364` 失败收尾置 rejected、`RejectReason=runErr.Error()`（='context canceled'），随后 `return runErr` → worker `MarkFailed` → `queue/direct.go:105-109` attempts 未达上限**回 queued 自动重试**；③ 重试跑 `ClaimTicketForRun`（P1-5 设计**允许 rejected 重认领**）后再进 workflow，`orchestrator/workflow.go:260-273` 的「驳回重翻循环」把**任何非空 reject_reason 当人工驳回意见**——首烧中止令全部译文为空，循环逐语种 `continue` 后 `savePayload; return nil`，后续步骤对空载荷同样空跑，Execute 返回 **nil**；④ `service/ticket.go:398-400` 见无错误即 `status=completed`（chargeTokens 归集 0 → tokens_billed=0），`store/ticket_finish.go:44/48` 无条件把内存里的旧 reject_reason 一并写回——「context canceled」以 completed 身份留库。对外侧 `api_openapi_tasks.go:439` completed 分支**不检查产物/abort 痕迹**，直接拼空 translations 回 200。

### F-43 【P3·对外文案向】开票被拒时把驱动层原始错误 `sql: no rows in result set` 拼进用户文案——待付单/他租户单两条路径活证

- **现象（生产实测，J8 补测轮）**：`POST /api/billing/invoices/create` 对**本租户待付单 7** 与**他租户单 5** 分别回 `200 {"success":false,"message":"开票失败（需订单已支付）: sql: no rows in result set"}`——面向用户的 message 直接带出 Go 驱动内部错误原文，且「订单未支付」「订单不存在/不可见」两种语义被同一句含糊文案混包（前者该说「仅已支付订单可开票」，后者按租户隔离口径不应确认存在性）。
- **根因（源码读死）**：`store/billing.go:1915-1929` CreateInvoice 两段 `QueryRow(...).Scan()` 的 `sql.ErrNoRows` 未做语义转换原样上抛（:1919 查 status、:1926 限定 `status='paid'` 查金额都会对不存在/不可开票单返回裸 ErrNoRows）；`api/admin_billing.go:420-423` 又把 `err.Error()` 拼进对外 message。同文件 refunded（:1922 `errTxt`）与重复开票（:1936-1937、:1946-1947 唯一索引冲突转可读错误）都有专门文案，唯独「查无此单/未支付」漏网——修复有现成范式。
- **风险**：驱动错误原文外泄属信息卫生问题（客户可据此分辨内部实现）；两语义混包让用户在「刚付的单怎么不能开票」场景拿到无法自助理解的话术。非资损、非越权（跨租户单本来就该拒，这里只是文案）。
