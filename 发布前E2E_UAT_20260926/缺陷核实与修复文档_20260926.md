## 一、批 I-1 ｜ F-44【P0】对照编辑保存在生产 100% 失效（唯一必修红线）

### 1.1 代码核实结论：成立，且比报告写的更确定

报告说「生产 PG 上必红」——已读到三条硬证据链，逐条坐实：

1. **驱动不做占位符翻译**。`go.mod` 锁的是 `github.com/lib/pq v1.12.3`（不是 gorm 也不是 pgx），该驱动**不认 `?` 占位符**。仓内唯一的 `?`→`$n` 翻译器是 `backend-go/internal/db/query.go` 的 `RewritePlaceholders`（逐字符扫，`case c == '?' && !inLiteral` 时写 `$n`），它**只在 `db.Query` / `db.Exec` / `db.QueryRow` 这三个包装函数内部被调用**（`pgTranslate` 分支）。绕过包装函数＝把裸 `?` 交给 PG。
2. **三处绕过点**（全部 `s.db.Query(...)` 直调，不走包装器）：
   - `internal/store/edits.go` `GetTranslationEdits`：`WHERE ticket_id=? AND lang=?`；
   - `internal/store/edits.go` `ListKBTerms`：动态拼 `AND target_lang=?` 与 `LIMIT ?`；
   - `internal/store/segments.go` `GetTicketSegments`：同一形状，且该文件注释里自己承认了这是历史遗留写法。
   对照面：**同文件的写入侧是正确的** —— `UpsertTranslationEdit` 用 `db.Exec(s.db, db.CurrentDialect(), q, ...)` 并按方言分了两条 SQL 分支，所以「保存返回 200 success=true」是真的写进了库，这就是「假成功」的机制来源。
3. **错误在 API 层被吞干净**。`internal/api/editor.go` 三处 `edits, _ := s.Store.GetTranslationEdits(...)`、`terms, _ := s.Store.ListKBTerms(...)`，以及 `handleExportSegments` 里同样写法；`GetTicketSegments` 的错误被当作「未命中」继续走（`if err != nil` 分支不返回错误）。生产日志里 PG 报的 `syntax error at or near "?"` 被 `logger()` 吞成 19 字节空壳，界面全绿。
4. **闸门扫不到**。`scripts/uat/api_uat_txn.sh` 的对照编辑段只断言了 `"success":true`、`"type":"file"`、`TranslatedEN` 三件事，**没有「存完再读回来比对」这一腿**；`editor_test.go` 只覆盖 4 个纯函数（分段/映射类），不碰 SQL。SQLite 本地快跑又是 `?` 的天然兼容方言 ⇒ 三层都不红。

**外溢范围（报告只写了对照编辑，实际是四条客户可感知链）**：修订重读、行级术语命中高亮、`handleExportSegments` 的 Excel/CSV 导出（导出会**静默丢掉人工修订列**）、`GetTicketSegments` 相关读路径。其中真实交付失真最重的是 `editor.go` 的审批回写导出分支（它按 `editMap[i]` 判断是否用 `e.EditedText` 覆盖机器译文 ⇒ 读回恒空＝**审批后导出的仍是机翻**）。

### 1.2 精确改法（按此顺序施工）

**第 1 步｜三处 SQL 改走方言包装器（`store` 层，只改读法，不改语义）**
- `edits.go` `GetTranslationEdits`：`s.db.Query(sql, args...)` → `db.Query(s.db, db.CurrentDialect(), sql, args...)`，并按 `UpsertTranslationEdit` 已有的范式**把 `?` 写成 `$1/$2`（PG 分支）与 `?`（SQLite 分支）两套**，或统一写 `?` 交给包装器翻译（包装器只在 PG 分支翻译，SQLite 分支原样透传，**这是更省事且更不易错的一种**：SQL 里保留 `?`，只改调用形式）。
  ⇒ **本批统一采用后一种口径**：SQL 串里写 `?`，调用改走 `db.Query/db.Exec` 包装器，由 `RewritePlaceholders` 按方言翻译。`ListKBTerms` 的动态拼接与 `segments.go` 同此处理。
- 施工纪律：AGENTS §一·4 明确禁止硬编码方言语法；改完必须**同一份代码在 SQLite 与 PG 各跑一遍**才算过。

**第 2 步｜API 层禁止吞错（`editor.go`，同时收敛 §一·8）**
- 三处 `_` 改为接 `err` 并 `s.writeError(w, r, apierrors.New(apierrors.ErrInternal, "读取人工修订失败"))` 一类的**带码错误**（禁止新写内联 `writeJSON(4xx/5xx)`，会顶红 `TestErrorStyleRatchet`）。
- `GetTicketSegments` 的 `err != nil` 分支：区分「确实无分段（返回空集合）」与「查询报错（必须上抛）」，二者现在被压成同一条路径，这是假成功的第二层。

**第 3 步｜把这类写法永久锁死（机制，比前两行更重要）**
- `internal/db/guard_test.go` 的 `rawSQLPatterns` 现在只匹配 `.DB()` / `RawDB()` 两种取裸句柄的写法 ⇒ `s.db.Query(` 这类**同包内直调原生句柄**是盲区。给它补一条：`\.db\.(Query|QueryRow|Exec)\(`，并对现存**合法**豁免清单（PG-only 的 `internal/kb/db.go`、`packages.go` 的 PG DDL 分支、`cmd/migrate-sqlite-to-pg`）显式白名单化，否则闸门起不来。
- 这条闸门是本批真正的收益来源：F-44 属于「同类错误已经第三次出现」的形态（`segments.go` 注释自证历史上踩过），只修三行不建闸＝下次换个新文件再犯。

**第 4 步｜补断言（缺一律视为未完成，AGENTS §三）**
1. **PG 方言下的「存完读回」闭环**（这条是唯一能抓 F-44 的断言）：在 `scripts/uat/api_uat_txn.sh` 的对照编辑段，把现有的三眼断言扩成 —— 保存修订 → 再调 `GET segments` → 断言返回体里出现**写入时那段自定义修订文本**（不是机翻文本）。当前脚本连 `translation_edits` 表都没查过。
2. **单测**：给 `GetTranslationEdits`/`ListKBTerms`/`GetTicketSegments` 各补一条在 PG 方言下跑的用例（按 §一·4 的教训**自钉方言**：`old := config.C; cfg := config.Default(); cfg.DatabaseDriver = "postgres"; config.C = cfg; t.Cleanup(restore)`，别只跑内存 SQLite）。
3. **吞错回归**：构造一次必然失败的读（例如把 `lang` 传成非法值），断言接口回带码错误而不是 200 空集合。

### 1.3 发版影响

## 二、批 I-2 ｜ F-45 反馈详情整页崩（运营侧可感知，止血成本一行）

### 2.1 代码核实结论：成立，全链逐环读到

- 后端 `internal/api/feedback.go` 的 `objectType=="ticket"` 分支：`_ = json.Unmarshal([]byte(t.FinalResult), &payload)` **错误被丢弃**，文件工单的 `FinalResult` 为空 ⇒ `payload.Translations` 是 nil map ⇒ `json.Marshal(nil)` 得到字面量 `"null"`，并且因为 `jerr == nil` 成立，这个字符串被**无条件写进 `feedbacks.translations`**。列定义 `translations TEXT NOT NULL DEFAULT ''`（`store.go`），空串是正常态、`"null"` 是毒值。
- 前端 `components/admin/TicketsP.tsx` 的兜底 `JSON.parse(f.translations_json || '{}')`：`JSON.parse("null")` 返回 `null` 且**不抛错**，所以 catch 不生效，`Object.entries(null)` 直接 `TypeError` ⇒ React 错误边界接管整页。点「重试」二次进入仍崩（非时序问题），与实测一致。
- 数据面等值已在生产实测确认：只有 `tj="null"` 那一行崩，文本工单行（有真译文对象）渲染正常。
- **附带两环也被证实**：① 同一分支里 `SourceText` 取自 `t.SourceText`，文件工单该字段为空 ⇒ 后台看不到原句；② 留资行 `user_id=0` ⇒ 列表用户列显示 `#0`（见 O-12）。

### 2.2 精确改法（三处必须同批，缺一处仍红）

1. **前端止血（一行，优先级最高）**：把兜底改成「解析后二次判型」——
   `const p = JSON.parse(x || '{}'); return p && typeof p === 'object' ? p : {}`。
   这一条改完，存量 `"null"` 行立刻能看（换 dist 即生效，不动二进制）。
2. **后端不再生产毒值**：`feedback.go` 里 unmarshal 的 err 不再丢弃（记 warn 日志并留痕），且在 `Translations` 为空时**写入空串**而不是序列化 nil map；即把 marshal 目标先做 `if payload.Translations == nil { f.Translations = "" }`。
3. **存量订正（幂等，需用户逐字批准后执行）**：
   `UPDATE feedbacks SET translations = '{}' WHERE translations = 'null'`；
   执行前先数：`SELECT COUNT(*) FROM feedbacks WHERE with_context = 1 AND btrim(coalesce(translations,'')) = 'null'`。
4. **补断言**：单测构造 `FinalResult=""` 的 ticket → 断言落库值不等于字面量 `"null"`；前端补一条 `*.dom.test.tsx` 用 `translations_json: "null"` 渲染详情面板不崩（断言渲染出内容而非错误边界文案）。

### 2.3 发版影响
前端止血＝换 dist；后端与存量 SQL＝换二进制 ＋ 一条批准后的 UPDATE。建议**同一批**做完，否则「新数据不再产毒、旧数据仍崩」是半修状态——本轮 UAT 已经证明这个项目的半修族（F-11/F-15/F-23/F-24/F-29/F-42）共性就是「修写侧不修读侧 / 修新账不订存量」，本文档把它当作施工纪律来防。

## 三、批 I-3 ｜ 运维高危三连：F-55（照屏点保存就把租户日限写成不限）→ F-56 → F-63

这三条同一形状：**「界面上看到的数」和「真正写进库的数」不是同一个源**，只有实跑才抓得出来。

### 3.1 F-55 配额表单读 A 写 B —— 成立，已读到决定性判据

- **读侧**：`internal/api/billing_api.go` 的配额 GET 用 `qu := s.authUser(r)`，取 `tid := qu.TenantID`（超管该值＝0），随后在超管视图分支里**回落成请求里带的 `max_daily_*` 现值或 0**；实测表现＝切到租户 3 后表单回 `0/0/100000/1000`，而库里真值是 `10/3/100000/20000`。

## 七、批 I-7 ｜ 状态码诚实族：F-47 ＋ F-64（先定口径，别急着扫 235 处）

## 九、批 I-9 ｜ F-46 首屏 2 MB：根因要加一条「存量值已超当前上限」

### 9.1 核实结论：成立，且多一条更硬的证据

- 注入链读死：`spa.go` 的 `serveIndexHTML` 每次请求都调 `s.brandingPayload(r)` 拿租户/平台品牌、`injectBrandingScript` 把整包 JSON 以 `<script id="__branding__">window.__BRANDING__=…</script>` 插进 `</head>` 前，并**无条件 `Cache-Control: no-cache`**。品牌图（`brand_logo`、`brand_home_bg`）在 `tenants`/`system_config` 里存的就是 base64 dataURL（列 `TEXT NOT NULL DEFAULT ''`），所以 HTML 体积＝图片体积。
- **新证据（比「设计如此」更该修）**：`tenant.go` 有 E15 批设的上限 `brandHomeBgMax = 1200*1024`（约 1.2 MB base64）、`brandLogoMaxLen = 420*1024`，且 `validateBrandPayloads` 在**唯一写入路径** `/api/tenant/branding` 上做了校验。而演示站实测 `brand_home_bg` dataURI 是 **2,065,807 字符 > 1.2 MB 上限** ⇒ 这一行存量数据是**在上限生效之前写入的**（或经该 handler 之外的路径写入），当前闸门只防新写、**不会缩小已存的值**。也就是说：即使现在什么都不改，这个租户也再也无法在后台保存品牌设置（一改就 400「过大」），而首页继续背 2 MB。
  ⇒ 这条把 F-46 从「性能优化」提升为「该租户后台功能已不可用」，建议纳入发布必修。
**改法（分两层，第 1 层不做完第 2 层没意义）**：
 1. **存量止血（必须人工批准）**：把演示站的 `brand_home_bg` 换成压缩后的 webp（目标 base64 ≤ 约 200 KB），或直接清空回落默认背景；同时确认 `brand_logo`（实测 11,026 字符，尚可）。这一步不需要改代码，只需一次后台保存（可能因校验被拦 ⇒ 需先改库或先降图）。
 2. **机制修（代码）**：品牌图**改为落静态件 + 只把 URL 注入 HTML**（`/uploads/brand/<tid>/home-bg.webp` 一类，`/assets/` 已有长缓存范式 `immutable, max-age=31536000` 可照抄），HTML 只存 URL；`serveIndexHTML` 对**无品牌定制**的域名（主站）走可缓存路径，仅对配了品牌的租户站留 `no-cache`。注意落文件后必须定义「品牌图 404 的兜底」（回落默认背景，别白屏）。
**补断言**：一条冒烟锁「首页 HTML 的 `decodedBodySize` < 30 KB」＋ 一条锁「`__BRANDING__` 里 `brand_home_bg` 若存在则必须是 http(s) URL 而非 dataURI」。**注意这是后端直出面（§一·5 第 ②/③ 类之外的 index 注入），动 `spa.go` 必须换 `translator-server`。**

## 十、撤案与「不要照报告施工」清单（最重要的一节）

这一节专门用来防止按《UAT报告》原文施工造成误伤。报告里这 5 条结论已被代码推翻或需降级：

1. **F-66 撤案（不是资损）**：`llm/client.go` 每次调用回调一次 → `billing_api.go` 缓冲 → `RecordUsageBatch` **逐次落一行**，而 `engine/text.go` 注释自证「fast/pro 均含校对环节」⇒ pro 一次投递出现 2 行是**设计**（初翻一行、校对一行），1 行的情况由校对跳过或去重路径解释。**禁止**按「重复计费」去加去重逻辑，那会真把校对环节的用量丢掉。

### 18.3 本轮新发现两条缺陷（待用户决策，本批一律未动产品行为）
**F-72 短文本「预估积分」系统性低估——公式没有固定开销项**
- 现象：19 字 × 1 语的 pro 单（工单 id 47）实烧 **18,304** token，而预估只有 19×1×160＝**3,040**，差 **6.0 倍**；同族小单普遍「估三五百、烧一两千」。

**F-76｜品牌域名登记不规范化、不查重、不预留：填错写法静默失效，前缀可被抢注**
- 根因（两处代码实测）：`internal/tenant/tenant.go` `SetBranding` 把 `domain` **原样 UPDATE 入库**（无 trim／无小写／不剥基础域／不剥路径／不校验合法性）；`internal/api/tenant.go` `tenantPrefixFromHost` 用 `strings.TrimSuffix(host, "."+base)` 得到**裸前缀**，`GetByDomain` 是 `WHERE domain=?` 的**精确等值**。两侧口径不匹配＝写侧宽松、读侧严格。
- 后果一（静默失效）：客户在管理台填 `ROX`、`rox.lexicorn.cn`、`rox.lexicorn.cn/` 甚至带空格，保存全成功、预览还好看，但真实访问永远解析不到品牌（回落平台默认），**不报错也没法自查**——这是最容易被当成"你们品牌功能不生效"的投诉来源。
- 后果二（命名空间无治理）：`GetByDomain` 未命中时 `resolveDedicatedTenant` 还兜底 `GetByCode`（见 F-77）⇒ 任何人可把**任意字符串**登记成自己的 `domain`，包括 `rox-test`（演示站前缀）与其他租户的 code；两个租户填同一前缀时没有唯一性校验，后写者是否生效取决于匹配顺序，属"两个人抢同一个门牌"。管理台预览又是 `${domain}.lexicorn.cn` 拼出来的，所以填错/填重都看不见真实后果。
- 为何不顺手改：涉及**存量行清洗**（现网 `rox`/`rox-test` 恰好都是规范小写裸前缀，改动要给清洗脚本与幂等迁移），且唯一性约束要决定"撞了怎么办"（拒绝保存＝对老库可能一上来就 400 别人在用的值），保留名单还要定范围（`www`/`api`/`admin`/`langcross`/`rox-test`/…）。
- 建议改法与前置：入库前统一规范化（trim＋小写＋剥 `.`+base_domain＋剥路径与端口＋字符集白名单，非法即 400 带明确文案）；新增唯一性判定（同前缀已被占用即 400，报错只说「该域名已被使用」不泄露是哪个租户）＋保留前缀名单（取 `primary_host` 与既有站点块前缀）；管理台把「真实生效域名」与「预览域名」同源显示，并在保存后回读一次 `tenantPrefixFromHost` 判据做自检断言；补 Go 单测钉「大写／整域名／带斜杠三种写法规范化后等于裸前缀且能被读侧命中」。前置＝确认是否要给历史脏数据留兼容读（建议不留，直接清洗＋一次性提示）。

**F-77｜专属域名注册的两条注释与实际行为相反，且 code 天然是个隐式域名（低危，但会误导下一个改这块的人）**
- 实测：`internal/api/tenant.go:346` 注释写「仅当…**非默认平台租户（code≠rox、id≠1）**」、`internal/api/register.go:74` 注释写「命中后注册…**免邀请码**」。逐行读函数体：`resolveDedicatedTenant` **既没有排除 id=1 也没有排除 code=rox**（只挡 apex／primary／主站前缀／非 active），而注册分支 `register.go:248-259` **强制要求企业邀请码**且必须属于该专属租户，缺码直接 400「请填写企业邀请码后再注册」。⇒ 两条注释**都是错的**，一个照注释施工的人可能以为默认租户不会被命中，或者以为专属域名免码注册是有意的安全设计而去"保护"它。
- 真正的行为风险有限但存在：`GetByDomain` 未命中时兜底 `GetByCode`，所以**任何租户的 code 自动就是一个可解析的子域**（`uateco01.lexicorn.cn`、`p_1788…​.lexicorn.cn` 都算"专属域名"），F-73 的通配块第一次把它送到公网。已实测品牌侧不受影响（GET `/api/tenant/branding` 对这两个 host 都回 `tenant_id=0`——品牌解析只认 `domain` 列），影响面只在注册：陌生人拿到该企业某个**未使用的邀请码**时，可以从一个客户从未申请、从未被告知的隐式域名把账号塞进该企业。
- 修法与前置（二选一，需用户定）：① 收敛命名空间——`resolveDedicatedTenant` 去掉 code 兜底，只认已登记 `domain`（代价：依赖 `code.品牌基础域` 访问的老部署要迁）；② 保留兜底但把两条注释订正为真实行为，并在管理台「品牌域名」旁列出"该租户 code 同时是可访问子域"的提示。无论选哪条，**注释订正都要做**（纯注释、不进直出面、不需为此换二进制）。
- 未做的验证：没对生产打注册 POST（会写 `regGuard` 的 IP 限流计数并可能留下真实账号），上述结论取代码路径＋品牌侧只读实测；本地若要做实锤，用 SQLite 起临时实例断言 400 与租户归属。

### 21.1 F-75 品牌展示付费闸（〇-W 只锁住保存，本轮补展示侧）

- **口径来源**：用户「租户要付费才能有品牌定制内容，付费＋配了品牌才会展示」。核实现网发现"企业根租户"本就不依赖套餐，所以四条腿缺一不可。
- **展示判定**（`internal/api/branding_paid_gate.go` 的 `tenantBrandingDisplayUnlocked`，调用点在 `tenant.go brandingPayload`）：①企业根租户 ②超管显式授权 ③套餐在效 ④到期后 30 天品牌宽限。天数优先序 `env BRAND_GRACE_DAYS` > `system_config.brand_grace_days` > 30，钳 [0,90]（0＝当天回收），非法值回退 30。
- **三条刻意的设计（后来者别"顺手优化"）**：
  1. **只摘视觉、不清库**：`hideTenantBrandVisuals(out)` 只改响应体。若在回收时把 `tenants` 的品牌列置空，宽限期内的任何一次管理台保存都会把客户真配置覆盖掉——"暂不展示"被做成"永久丢失"，这是不可逆的账。
  2. **超管永远看真值**（`brandingViewerExempt`）：否则超管进品牌面板看到的是空配置，凭"我给他配好了"点保存就写回一份假的。
  3. **只对匿名访客摘**：登录用户看到的是自己租户的真品牌，不受展示闸影响。
- **宽限期落库**（`internal/store/branding_grace.go`）：三键写进 `tenants.permissions` JSON（`brand_grace_expires_at` / `brand_grace_notice_start` / `brand_grace_notice_end`），**不新增列⇒无需幂等迁移**，老库直接兼容；一律 `db.JSONPatchSet` 单字段原子更新（整体回写 permissions 会把快照之后的并发续订/额度调整覆盖掉，这是 B1 那批整改的口径）。**不复用 #74 的订阅续费宽限**：那套默认 3 天且只给开了自动续费的租户，而品牌回收是对所有靠付费解锁品牌的租户生效的商业动作，混用会让未开自动续费的租户永远进不了宽限。

### 21.11 ★ F-79「显式 `?tenant_id=` 可跨域读到别的租户品牌」——**已于 09-28 〇-Y 修完并上线**（施工与验收读数见 §二十二）

> 本节以下五条是**登记时的原始取证**（现象/根因/后果/为什么不顺手改/修法前置），保留不改，供后人知道当时怎么判的；
> 现行口径以 §二十二 为准：**修法就是下面「修法前置①」那条建议原样落地**（忽略参数、不返 403），
> 且已带三条自动化断言与线上只读复核。

- **现象**：`GET /api/tenant/branding?tenant_id=1` 从**任意域**（主站、演示站、甚至别的租户的品牌域）都能拿到该租户的品牌配置（logo/背景图/名称/登录页形态），不需要登录、不需要是该租户成员。用浏览器在 `rox-test.lexicorn.cn` 上把前端参数改成 `tenant_id=1` 即可复现，响应 200 且带真品牌字段。
- **根因**（读代码核实，非推测）：`internal/api/tenant.go handleTenantBrandingGet → brandingPayload(r)` 的解析优先序是「显式 `?tenant_id=` ＞ 按访问子域前缀 ＞ 平台默认」。**第一条分支直接 `s.Store.Tenant(id)` 取数，没有校验访问者的 Host 或身份**；F-75 的展示闸（`brandingViewerExempt`/`tenantBrandingDisplayUnlocked`）在这条路上照样执行，所以"付费没付"不是问题，**"该给谁看"才是问题**。按域解析那条路径（第二条）本来就是域隔离的，没有这个洞。
- **商业后果**：我们对外承诺的是「品牌只在其品牌域生效」（客户买白标要的就是这个）。这条承诺目前**是前端选 URL 保证的**：`frontend-react/src/branding.tsx` 只在显式传入 `tenantId`（超管后台切换租户预览/编辑）时才带这个参数，普通页面不带。服务端没兜底＝客户可以合理质疑，且竞对可按 id 枚举拉取已付费客户的品牌资产（背景图/名称本身即商业信息）。
- **为什么不顺手改掉**：① 这是**公开端点的契约变更**——未登录可达的接口，改成"显式 `tenant_id` 只对超管放行"会立刻改变响应形态，必须同时确认没有第三方集成方/嵌入方在用它做多租户预览（现网日志与 OpenAPI 文档口径要核）；② 修法要自带断言才算完成（AGENTS §三：修缺陷必须补能复现的自动化断言），且新断言得同时覆盖"超管预览这条正路不能被误杀"，属独立一批施工＋发版；③ 收尾批的原则是"文档与代码同步、不夹带未验证的对外契约变更"。**夹带过一次现网 500 的教训在前（F-64 那批），这次不冒。**
- **修法前置（拍板后即可执行）**：① 判据先定——建议「显式 `tenant_id` 仅当访问者是超管（或该租户自己的成员）时生效，否则忽略该参数、回落按 Host 解析」，**注意不是返回 403**：匿名访客在公开页会带一个不属于自己的 `tenant_id`（历史链接/收藏夹），403 会把正常首屏打坏，忽略参数是更安全的降级；② 取证一步：翻近 30 天访问日志统计带 `tenant_id` 的匿名请求占比与来源（若为 0 则契约变更零风险）；③ 断言两条：Go 单测（跨 Host 打 `?tenant_id=` 必须回平台默认或本域品牌；超管会话下必须回指定租户）＋UAT 一条匿名锁；④ 与 `branding.tsx` 的超管预览入口同批验证，避免"修好了 API、管理台预览废了"。
