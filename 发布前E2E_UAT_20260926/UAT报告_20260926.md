## 四、缺陷清单（因果链·交用户决策·本轮未改一行代码）

### F-44 【P0·客户可感知假成功＋交付失真】对照编辑保存＝假成功，修订与审批全部丢失

- **现象（四腿闭环）**：① UI 编辑→保存 → `POST /api/tickets/segments/save?id=92&lang=en` → **200 `{"saved":1,"success":true}`**，随后 `GET /api/tickets/segments?id=92&lang=en` 回 `edited_text:"" / status:"" / note:""`，审批下拉回显「待处理」；② 绕开 UI 以真实差异报文直连接口（`{"edits":[{"index":0,"edited_text":"API-LEVEL-PROBE edited translation 11.11 CNY 299.","status":"approved","note":"uat-note"}]}`）→ 同样 `{saved:1}`、同样读回全空 ⇒ **与前端/脚本手法无关**；③ 交付侧连带失真：工单 92 下载产物 `xl/sharedStrings.xml`（403 B 解包）里仍是机翻原文「…on Double Eleven…」，不含任何修订串；④ 历史面全灭：09-25 曾判 PASS 的工单 76（当时保存过审批＋编辑）与文件工单 84，本轮读回「非空编辑段数=0」⇒ 生产库中既有全部在线修订均不可见。
- **根因（代码级，只读定位）**：写侧 `UpsertTranslationEdit` 走方言层 `db.Exec(s.db, db.CurrentDialect(), q, …)`（`backend-go/internal/store/edits.go:53`），PG 下占位符被正确改写、`INSERT…ON CONFLICT` 成功；读侧 `GetTranslationEdits` 用**裸连接** `s.db.Query(...)` 且 SQL 里写 `WHERE ticket_id=? AND lang=?`（`edits.go:59-61`）——绕过 `db.RewritePlaceholders`（`internal/db/query.go` 的 `?→$n`），PostgreSQL 直接语法错；调用方 `edits, _ := s.Store.GetTranslationEdits(id, lang)`（`internal/api/editor.go:95`）把错误吞掉 ⇒ 永远空。同文件 `ListKBTerms`（:93）同型裸 `?` ⇒ 线上 segments 响应 `"terms":null`（术语高亮是同一条腿的连带）。这正是 AGENTS §一·4 点名的历史高频踩坑。
- **为何不能直接修**：① 写侧成功、读侧吞错，界面与告警都没有红灯，改一行 SQL 就动到 store 冻结域（`edits.go` 属被 46 个 api 文件 import 的包），必须同批补断言；② 存量库里「曾经写成功」的修订行是否真在表中（`ON CONFLICT` 是否落了 PG）需要一次只读 SQL 体检——如果写侧其实也只在 SQLite 有效，修法还要多一步数据回捞；③ 交付链路（下载/回写）是否应在产物里叠加 `edited_text` 是**产品口径**（现在证据显示产物只含机翻稿），单独改读法不改交付反而会造成「界面上看得见、下载到的还是旧的」新割裂。
- **修法前置**：`GetTranslationEdits`/`ListKBTerms` 改走 `db.Query(s.db, db.CurrentDialect(), …)`；断言从「save 返回 `{saved:n}`」升级为**「save 后 GET 等值回显 ＋ 交付产物含修订串」，且必须在 PG 方言下跑**（AGENTS §一·7 末条：`DB_DRIVER=sqlite` 快跑不是发布闸门）；顺带把吞掉的 error 冒泡成告警。补一条 `200 承载失败` 反向断言（见 F-64）。

### F-45 【P1·运营侧整页崩】文件工单类反馈一点开就把整个后台送进错误边界

- **现象（实读）**：`url=/admin ;; region=页面出现异常 | Cannot convert undefined or null to object | 重试 | 返回首页 ;; buttons=重试 / 返回首页`；点「重试」二次进入**仍然崩**（`recovered=true ;; afterSecondClick=页面出现异常`）⇒ 不是渲染时序，是**同一条反馈永久打不开**，且崩的是整页（列表、其它反馈、审批台全不可达，只能「返回首页」重进）。正向对照：反馈 1008（文本工单）详情正常渲染 `[en] Our store is offering a huge promotion on Double Eleven, with all products available from as low as ¥299. We accept payments via Alipay and WeChat Pay.`，且 `¥299` 未被错译成 `R299`。
- **根因（两段拼接）**：`backend-go/internal/api/feedback.go:89-106` —— `objectType=="ticket"` 分支里 `_ = json.Unmarshal([]byte(t.FinalResult), &payload)` **错误被吞**；文件工单的 `FinalResult` 为空 ⇒ `payload.Translations` 为 nil map ⇒ `json.Marshal(nil)` 出**字面量 `"null"`** 存进 `feedbacks.translations_json`。前端 `frontend-react/src/components/admin/TicketsP.tsx:104-106` 的兜底 `JSON.parse(f.translations_json || '{}')` 对 `"null"` 无效（`JSON.parse("null")` 返回 `null` 而不抛错），`:231` 的 `Object.entries(null)` 直接 TypeError ⇒ 错误边界接管。
- **数据面等值取证**（`GET /api/feedback/list` 200 逐行）：`#1007/wc=true/tj="null"/src=""` | `#1006/wc=false/tj=""` | `#1005/wc=false/tj=""` | `#1008/wc=true/tj="{\"en\":…}"` ⇒ **只有 `tj="null"` 那行崩**，空串行不崩（走的是另一条兜底）。
- **为何不能直接修**：任一侧单独改都可能让存量 `"null"` 行仍然红——只改后端不清存量，1007 照样崩；只加前端兜底则后端继续生产脏数据。修法必须把「存量订正」算进同一批。另外 `#1007` 的 `source_text` 也是空串（文件工单原文未随上下文带出），要一并决定后台是否该看到原句。
- **修法前置**：① 前端止血（一行）：`const p = JSON.parse(x||'{}'); return (p && typeof p==='object') ? p : {}`；② 后端 `feedback.go` 落库前判空（写 `"{}"` 或不写）并把 unmarshal 错误如实留痕；③ 幂等订正 `UPDATE feedbacks SET translations_json='{}' WHERE translations_json='null'`；④ 断言：单测构造 `FinalResult=""` 的 ticket → 断言存 `"{}"`；vitest 对 `"null"` 的渲染不崩。

### F-46 【P1·发布面性能】演示站首页 HTML 单页 2,080,056 B，且每次路由都要重下

- **字节实测**（`performance.getEntriesByType('navigation')`，两次采样）：`decodedBodySize = 2,080,056 B`（**主站同路径 2,594 B，差 802 倍**）；`transferSize ≈ 1,540,394 B`（zstd）；`cache-control: no-cache`、`cf-cache-status: DYNAMIC`；TTFB/总耗时 = `410 ms / 1,742 ms` 与 `794 ms / 3,385 ms`。
- **构成定位**：HTML 内 99.8% 是内联 `window.__BRANDING__=` 赋值 —— `brand_home_bg` 为 **2,065,807 字符**的 `data:image/webp;base64,…`，另含 `brand_logo` 11,026 字符 PNG data URI（`tenant_id 1 / domain rox-test / 品牌「极石」`）。
- **影响（客户可感知）**：品牌注入按请求写进 HTML ⇒ HTML 不可缓存，演示站访客每点一次路由重下约 1.5 MB，首屏 TTFB 抖到 800 ms 级；公开演示场景会被读成「产品很慢」。**主站首页未配品牌大图，不受影响**（射程限于已配品牌背景的租户站＝当前演示站）。
- **根因（只读定位）**：品牌资源以 data URI 内联进服务端直出的 index.html（`internal/api/spa.go` 品牌注入路径），未落静态件。
- **为何不能直接修**：属后端直出面（AGENTS §一·5 五类渲染面之②）——改 `spa.go` 即改二进制、要换 `translator-server` 发版；且需产品定「大图改 URL 后，品牌图 404 时怎么办」的兜底口径，不能只改注入方式。
- **修法前置**：`brand_home_bg`/`brand_logo` 落静态件（如 `/uploads/brand/<tid>/home-bg.webp`）＋长缓存（`immutable` 或带版本 hash），HTML 只存 URL；顺带把无品牌租户的 index.html 从 `no-cache` 改为可缓存路径；改后按 AGENTS 口径换二进制并跑 `deploy/` 冒烟。

### F-47 【P2·契约/可用性】登录限流回 400 而非 429，且不带头 `Retry-After`

- **现象**：第 6 次（正确口令）→ **400／113 B** `{"success":false,"code":"RATE_LIMITED","message":"登录尝试过于频繁，请稍后再试","trace_id":"fcbb14bc9a93…"}`；第 7、8 次同 400，响应头 dump **无 `Retry-After`**。
- **根因**：`backend-go/internal/errors/codes.go:113-114` 把 `ErrRateLimited` 与 `ErrValidation` 归入同一 `http.StatusBadRequest` 分支；而**同仓另有相反写法**（`internal/api/auth.go:336/417`、`email_verify.go:184` 直接 `writeJSON(w, 429, …)` ＋ `w.Header().Set("Retry-After", …)`）⇒ **两类限流响应口径不一致**，前端/SDK 无法按状态码分支处理「稍后再试」与「参数错」。
- **为何不能直接修**：改动会把既有 400 断言打红（UAT 矩阵与前端分支都按 400 写过），需要与整个限流家族（登录/验证码/QPS 闸）一次性统一，属跨文件批次而非一行。
- **修法前置**：`ErrRateLimited` 单独映射 429 并带 `Retry-After`（=锁剩余秒数）；`loginLocked` 走同一口径；同步 `scripts/uat/*.sh` 与前端分支；顺带决定「不存在用户名不记失败（`auth.go:85-88`）、停用账号不记失败（:116）」是否为期望行为（现状＝爆破预算只被「口令错」消耗，且停用账号回 **403 `FORBIDDEN`「账号已停用」** 而非 401）。

### F-48 【P1·客户可感知】F-11 只修了一半：批 G 修的那条被 CSS 隐藏，客户在看的余额条仍停旧值

- **现象**：`span.pkg-line-tag`（批 G 修复靶点）实测**已即时刷新**为「2,145 积分 ≈ 1,287 句单语言」，但 `getComputedStyle().display === "none"`（`src/styles/mobile.css:25 @media(max-width:900px)` 隐藏顶栏徽标，本轮实测视口 841 px）；客户真正在看的工作台余额条 `[data-testid=chat-balance]` 停在「余额 2,064 积分 ≈ 1,238 句」、`chat-usage` 停在 8,563，翻译完成后 **6 s／36 s 两次复读均不变**。

- **两种坏形态**：窄屏＝唯一可见的那条是旧的；宽屏（>900px）＝同屏两条互相矛盾的数字（徽标新、余额条旧）。附带文案口径也不一致：徽标「… 句单语言」vs 余额条「… 句」。

### F-49 【P1·对外账务契约】`points_used` 少报一半，同步接口报 0

- **现象**：15 字 fast 单 → done 帧 `points_used: 9`、reply 尾「⚡ 本次翻译消耗 token：2705」，而台账 6461 `cost_points=18 / quantity=5,410`；开放 API 状态帧同样 `points_used: 9`，而台账 6466 `cost_points=18/5,432 tok`、余额 1,984→1,966 恰 18；**同步 `/openapi/v1/translate` 成功却回 `points_used: 0`**（「你好」→ `translations.en="Hello"`、`points_used:0`，真扣 18＝6465）。
- **根因**：done 帧只计了一条 LLM 调用的量，扣费按整条流水线（初翻＋校对）合计；同步接口成功路径未回填计费字段。
- **为何不能直接修**：这不只是显示问题——它是**对外契约字段**，改了会影响已在按 `points_used` 记账的老客户（他们现在少记一半，改正后账单会「突然翻倍」），需要与《计费口径》公告/文档同批发。
- **修法前置**：统一以整流水线合计回填 `points_used`（流式 done、`/tasks/status`、同步 `/translate` 三处）；补断言「三处 `points_used` ＝台账 `cost_points` 等值」；若要对老客户灰度，需在 `/openapi/docs` 写明变更与生效日。

### F-50 【P2·违反自家硬约定】公开接口载荷里带 token 裸值＋自相矛盾模式文案

- **现象**：done 帧 `reply` 正文尾部服务端直出「📊 模式：纯模型翻译 | 🎓专业校对模式 / ⚡ 本次翻译消耗 token：2788」；同步 `/translate` 的 `"mode":"纯模型翻译 | ⚡快速模式（AI初翻+校对）"`（同字段两口径）。界面 structured 视图丢弃 footer 所以不外显，**但线上载荷带着**，且任何直连客户（扩展/移动壳/未来的第三方）都会看到。
- **根因**：footer 由后端生成并塞进 `reply` 文本，前端渲染时过滤、后端未过滤。
- **为何不能直接修**：属 AGENTS §一·5「公开接口零 token 裸值、统一积分口径」的直接违反（P0 级约定违反，但用户可感知面小），修法是后端不再产出该 footer——需先确认没有任何前端功能/客户脚本依赖这段文本（它是历史「明细行」的唯一来源）。
- **修法前置**：后端 footer 拆成显式字段（`mode`、`points_used`）而非文本尾巴，`reply` 只放译文；`mode` 枚举单一真值；补公开接口负向断言「响应体正则匹配 `token：[0-9]+` 即红」。

### F-51 【P1·账单透明度/纠纷向】API 消耗流水 `user_id=0` ⇒ 客户在「我的用量」里看不到

- **现象**：同步 `/openapi/v1/translate` 那笔 6465 `cost_points=18` 的 `user_id=0`，而租户自助台账 `GET /api/billing/my/ledger` 按自己 user 过滤 ⇒ 客户界面看不到 API 消耗，只有超管 `/api/billing/usage` 看得到。本轮实测：eco 侧「我的余额」卡面值与永久桶对得上，但 API 那两笔只出现在超管面。
- **根因**：开放 API 无登录用户上下文，写流水时未回填「归属用户/归属 key」。
- **为何不能直接修**：要定口径——记成「key 的创建者」、还是「租户级公共桶」，两种改法对现有报表/对账单的影响不同；且与 F-49 是同一批改账动作。
- **修法前置**：流水加 `source`（`web`/`openapi`）与 `api_key_id`，`my/ledger` 增加租户级可见性（按 `tenant_id` 而非 `user_id` 过滤开放 API 行）；用量台账加一列「来源」。

### F-52 【P2·前端文案】chat 路径把 4xx 错误体的整段 JSON 直进气泡（含 trace_id 与内部码）

- **现象**：16,500 字触发后端 400 后，气泡文案＝「请求失败 (400): {"success":false,"code":"chat_text_too_long","message":"文本过长…","trace_id":"ddcc…"}」，**没有**像登录/工单路径那样取 `message` 上屏（对照：R3.4 的 `QUOTA_EXCEEDED` 经 `lc-toast` 显示的就是干净 message ⇒ 该缺陷是 chat 路径独有）。
- **根因**：SSE/fetch 错误分支把 `response.text()` 原样拼接，未走统一错误体解析。
- **修法前置**：chat 错误分支复用全局 `parseError → message` 路径，`trace_id` 只进「复制诊断信息」而不进正文；对 12 语种站点需按 `X-App-Lang` 取本地化文案（R0.10/#12 回归已证后端支持）。

### F-53 【P2·闸门口径】敏感词拦截回裸键名 `sensitive_blocked`，无 `error_code`、无可读文案

### F-69 【P2·发布面】12 语种手册 PDF 无公网下载面（判据改判）

- **现象**：`/docs/manual` 回 **200／2,591 B**，但实读是 **SPA 兜底壳**（含 `<script … src="/assets/index-BOIA4YDV.js">` 与 `tenant_id:0` 的 `__BRANDING__`）⇒ 手册 PDF **没有公网下载入口**；本轮 R0.5/R9.2 的「逐语种 `%PDF` + `application/pdf` + >20 KB」探针在公网**不可执行**，改以仓内 12 份 PDF 实物＋批H 铺库账（线上落 `/opt/translator/data/manual`，仅服务端可读）代证。
- **⚠ 判据纪律**：这正是 AGENTS §6 的兜底陷阱——「200」对托管物不是有效断言，必须「200＋非 HTML＋魔数＋体积」。
- **修法前置**：若产品要对外提供手册下载，需在 `spa.go` 增一条公网静态路由（当前未挂该目录）并配缓存；否则把「手册仅服务端留档」写进对外文档，别让人再按 `/docs/manual` 找 PDF。

### F-70 【P3·观察】API Key 轮换会重新分配 id 并清零 `call_count`

- **现象**：`POST /api/apikeys/rotate {id:35}` → 200 回显新串，列表项变成 **id=36**（旧行不再存在），计数归零。
- **影响**：若客户系统里存的是 key **id**（例如用 id 做限额或审计关联），轮换即断引用；运营侧看板的「该 key 历史调用量」也被清零。
- **修法前置**：轮换改为「同一 key 记录换 secret＋保留 id 与历史计数」，或在 UI 明示「轮换会重置用量统计」；至少把它写进 `/openapi/docs`。
